# 客户需求落地顺序与验收

本页是原功能计划/提交过程记录，不是当前工程整理五批的待办清单。probe、帧策略、水印、固定多输出和显式类型 SEI 已有实现；本页“第一/二/三批”及旧 pin/SDK/提交/复审状态属于各自窗口。当前合同从[文档索引](README.md)进入，最新源码绑定与尚未验证项见[核心整理验证](validation-core-refactor.md)，不按下文历史提交建议自动提交/发布。

本计划承接现有用户需求；`pipeline-design.md` 的 `/v2/jobs` 和模块命名是实现建议，不是额外的客户合同。响度统计仍只保留内部接口，不实现算法。

1. 第一批：完成带缓存的快速探流、确定性视频选择和错误/取消传播；保存依赖源码/配方及 SDK 安装产物摘要，拒绝跳过构建时复用失配库。验收 packet ledger、像素、PTS、8/10-bit、B 帧、短 EOF、分数帧率、晚音轨及 RTMP/SRT 连接连续性。复用现有 CI，不增加 workflow。
2. 第二批：先以独立提交搬运时间轴/帧身份职责，再加入随源 I、最大 GOP、保护帧和因果抽帧策略。验收源空洞、回绕/重复/缺失、短 B 组、降级恢复及持续过载终止；VVenC 逐帧控制在匹配的 fork 中实现。
3. 第三批：水印资源准备与有界缓存、静态合成和 required 起播门槛，再加入 GIF 和运行中资源/布局 revision；失败不能输出合同禁止的裸流。
4. 后续：依据实际需求实现多输出及各分支预算/失败隔离，再处理动态配置/规格重建；SEI 谱系和 SCTE-35 节目事件通道依赖明确的时间映射，分别验收 payload/section 与媒体时间。

按有独立验收价值的功能批次审查；纯重构与行为变更在提交层分开。FFmpeg/VVenC 保留独立提交历史，父仓库只在库提交后更新 gitlink。完成一批后先独立审计，不自行合入或部署，不因单个文件拆分 PR，也不同时推送一串未验收版本触发 CI。

## 历史提交拆分建议（已由用户确认的上述完整检查点取代）

1. 先在 FFmpeg 提交第一批的 buffered probe/预算/错误传播及对应 avformat 版本，父仓第一批再引用该精确 gitlink，并提交 SDK 凭据、探流接入和验收；此中间状态继续使用原 VVenC，不提前引入第二批的类型合同。
2. 第二批先在 VVenC 的 `live/v1.14.0` 提交逐帧 forceIntra/短组普通 I；再在 FFmpeg 提交 `live-frame-intra` 两个 wrapper、实际类型统计与 avcodec 版本。
3. 父仓第二批先保留纯策略核心/配置模块及相应测试的独立提交，再提交管线/worker 行为接入、同时更新两个匹配 gitlink，并纳入回归、文档和 SDK/Build ID 证据。CMake 等混合文件需按功能拆分提交，不能让中间提交引用尚未提交的库或保留旧 hook 断言。
4. 以上只规划提交粒度，不按单个文件拆 PR，也不推送一串未验收版本触发 CI。独立复审通过后再确定最终提交/推送动作；库历史始终独立于父仓。
