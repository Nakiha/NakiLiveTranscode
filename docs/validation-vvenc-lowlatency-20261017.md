# VVenC 3B / 2 秒 GOP 低时延首轮验证

历史验证窗口：本页的“当前/最新”、pin、SDK、提交/复审状态及未运行项只指下述那次源码与环境。当前工程整理候选及未验证项见[核心整理验证](validation-core-refactor.md)，能力/草案见[文档索引](README.md)。原始结果、数值和失败尝试不回写。

用户约束按 **PTS 显示顺序 I BBB P BBB P…** 验收，关键帧约每 2 秒一次；GOP 尾部及 EOF 可有短 B 组。不是把所有 inter picture 标成 B 的 low-delay B 模式，也不是关闭 B 帧。

## 环境和测量边界

本机 WSL Ubuntu 24.04，FFmpeg n9.0.2 fork、VVenC v1.14.0 的 pin 均未改变。输入为生成的 H.264 8-bit、320×180、25fps、B3、175 帧，按 DTS 实时回放；输出缩放 256×144、YUV420P10LE、VVC MPEG-TS，faster、2 个编码线程、目标码率 1.5Mbps，默认待命 worker。每个 profile 重复 2 次；证据 `out/vvenc-latency-f8fx1grp/`，包含配置、首帧日志、输入/输出视频、独立解码帧型、逐帧时延及状态。源码、动态库和参数记录在项目与 SDK pin 中。

“请求到首输出”始于完整 HTTP 请求进入 handler，止于首个编码包 mux flush；不包含客户请求上传、源采集与播放器显示。每帧 ingress-to-mux 始于 av_read_frame 后应用接收包，探流阶段已缓存的网络数据不按其真实 socket 入站时刻重新关联。

## 结果

| 配置 | 请求到首输出，两次 | 首输出对应帧 encode_ms | 首输出前喂入编码器帧数 | 全帧 ingress-to-mux 均值 |
| --- | --- | --- | --- | --- |
| reference，旧 GOP32 | 3295 / 3286 ms | 2601 / 2600 ms | 81 / 81 | 2794 / 2782 ms |
| live_3b_2s，默认 | 447 / 446 ms | 347 / 348 ms | 9 / 9 | 426 / 425 ms |
| live_3b_2s_no_mctf | 455 / 451 ms | 356 / 352 ms | 9 / 9 | 424 / 423 ms |

默认配置的输入 I 帧 ingress-to-mux 均值约 455–457ms、最大约 508–516ms；旧配置约 2972–2981ms、最大约 3441ms。输入 I 与 VVC 输出关键帧是不同的帧集合，不能混用统计。服务另外提供 `output_key_stages` 的累计及窗口各阶段指标，专门覆盖输出关键帧。

旧配置的主要耗时是前瞻/重排链路等待，不是文件打开或 I 帧连续占 CPU 2.6 秒：文件打开/探流完成约 4–12ms，第一帧解码出现在请求后 85–94ms（B 帧源输入也有必要重排），编码器初始化约 10–12ms。旧配置在首包前累计编码 API 墙钟仅约 42–65ms，API 之间仍需按实时节奏等待输入。旧首输出包对应输入 PTS 0.6 秒，日志的 worker_to_packet_ingress 包含等待这一个被选中的帧，不能整段算作探流。

新配置首输出对应首个输入画面 PTS 0；预分析与正式 GOP 编码阶段的源码各有 GOPSize+1 的队列门限，实际首输出前接受 9 帧。由观测和源码推断，当前剩余等待主要仍是两段短窗口、输入解码重排和计算共同形成；并不是 9 帧都在同一时刻排队，也不是固定 sleep。进一步压缩需修改/重组库内前瞻，并验证码控质量。

## 配置选择与实际码流验收

- 显式 custom GOP4：P4/B2/B1/B3 编码顺序，对应显示顺序 I BBB P…；首帧 POC0IDR，关闭 STA，不按场景额外插 I。
- IntraPeriod 直接设为 `round(2 × nominal_fps)`，避免 VVenC 秒数模式把 25fps 的 50 帧自动调整成 48 帧。实码关键帧索引 0、50、100、150，PTS 间隔均 2 秒。30000/1001fps 验证为 60 帧 / 2.002 秒。
- 保留单遍码控及 LookAhead，没有改成固定 QP；关闭 frame-parallel 队列，保留 2 个帧内编码线程。
- MCTF 只参考过去帧，QPA 保留。关闭 MCTF 没有稳定额外收益，默认保留。此次 custom P-anchor + MCTF + BIM=1 在 320×180、10-bit 样本上可复现 C++ 异常，CLI 也复现；BIM=0 后通过，因此本 profile 固定关闭 BIM。未声称修复了该库内问题。
- H.264/HEVC 的 8/10-bit、缩放/不缩放、MPEG-TS/MP4、UDP 输出、分数帧率、单帧排空均通过。独立 n9 VVC decoder 核对总帧数、显示帧型、关键帧索引和实际 PTS 间隔，验证重排后的输入帧关联、I/输出 key 的阶段统计。live profile 对量化后 PTS 跳帧明确失败，不悄悄拉长关键帧时间间隔。

另外实际测试 UDP 输入 → VVC MPEG-TS：请求到首输出约 407ms，input open 结束约 26ms、探流结束约 326ms、首个 encoder submit 约 341ms。探流期间已经读入一批网络数据，因此随后的编码喂帧比实时文件回放更集中，这个数不能直接用来宣称网络模式比文件模式更快。测试最终取消直播，独立解码帧数与成功写出计数一致，对完整首个 GOP 和下一个关键帧核对 3B 与关键帧周期；取消可能只写出末组的未来 P 锚帧，尚未写完 B 帧，因此不把不完整尾部当作正常 EOF 验收。上面的正常 EOF 样本仍严格核对全部输出帧。

这是一轮小样本正确性与等待来源测量，不是 1080p/4K 实时容量、画质、码率误差或 7×24 稳定性结论；没有声称达到客户私有实现中的“100ms 等待 + 60ms I 帧编码”。我们没有该私有 patch，也没有借其实现推断公共版本的内部语义。

复现：`python3 tests/vvenc_latency.py`；CI 用 `--repeats 1` 验证行为并保存证据，不用绝对毫秒阈值卡共享 runner。
